### 1.4 主要业务流程

| 流程                           | 路径                                                                                                                              | 要点                                                            |
| ------------------------------ | --------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------- |
| **导入**                       | 拖放/选择器 → `book_import`（`spawn_blocking` 逐文件）→ SHA-256 去重 → 解析元数据+封面 → 文件落盘 → 事务写 `books`+`chapters`+FTS | 事件 `book://import-progress`；PDF 的正文推迟到后台 `backfill`  |
| **阅读（两条通路，一份语料）** | foliate 通路（EPUB/MOBI/AZW3，CFI 锚）· Document Model（PDF/FB2/CBZ/TXT/MD，章 idx + 偏移锚）                                     | 导入期就抽好纯文本，所以检索 / RAG / 朗读两侧共用同一份语料     |
| **标注**                       | DOM 选区 → `selection.ts` 转 UTF-16 区间 → `annotation_create`                                                                    | EPUB 另存 CFI；偏移是**前端计算、前端解释**，后端只做不透明存储 |
| **查词**                       | 平台词典（macOS）→ 导入的 StarDict/MDict → AI 兜底                                                                                | 前两级全离线免 Key；三态标记值 `Found/Missing/Unavailable`      |

| **同步**                       | WebDAV 单 `state.json`：进度按 `content_hash` 对齐，标注/书签按 UUID，LWW + 墓碑                                                  | 云端解析失败直接中止，不覆盖本地                                |

## 二、新功能建议

排序按「解决问题的硬度 × 与定位的契合度」。每条都标了**大致改动范围**（文件数 + 是否需要新依赖）。

### F1　扫描版 PDF 的 OCR —— 走已配置的 AI 视觉端点　`P1`

- **问题**：ARCHITECTURE 自己列的唯一功能硬缺口——纯扫描 PDF 没有文字层，**既不能划选也不能问 AI**，
  上一轮审查也写了「值得重估：这是 PDF 用户最常撞到的一堵墙」。目前读者的出路只有「忍着」。
- **思路**（关键是**不引入任何新依赖**）：
  1. 前端已有 pdf.js 的 canvas 渲染，也有 `webview_capture_region`（仿真翻页那轮加的原生截图）——
     取一页的 PNG 字节已经有两条现成的路；
  2. `ai/` 已经是「OpenAI 兼容 `/chat/completions`」客户端，**同一个协议本来就支持 vision**
     （`image_url` 内容块）。新增 `ai/vision.rs`：把页位图 base64 后按「逐字转录，保留换行」提示词发出；
  3. 回填走既有通路：PDF 的「章即页」，把识别出的文本写进 `chapters`（`chapterIdx = page - 1`），
     `chapters_fts` 的触发器自动接管索引，于是**检索 / RAG / 朗读 / 问 AI 四条链路同时活了**；
  4. 文本层补上后 `pdfTextSelection.ts` 不用改——它本来就按文本层工作。
- **契合点**：「AI Native」（能力来自已配的端点）＋「不打包数据集」（不引 tesseract / onnxruntime，
  能指本地 Ollama 的 vision 模型）。没配 AI 时入口不出现，Local First 不受影响。
- **优先级**：`P1`。**改动范围**：新增 `ai/vision.rs` + `commands/ocr.rs`（1 条命令）+ 前端 PDF 面板一个入口
  - `bindings.ts` 重新生成；约 4–6 个文件，**0 新依赖**。
- **风险**：长文档按页调用成本高 → 先做「本页 / 本章」，整本走后台 + 进度事件（复用 `rag://index-progress` 的形状）。

### F2　换版本 / 重导入时迁移阅读状态　`P1`

- **问题**：`content_hash` 既是身份键也是去重键。**同一本书改了一个字，重新导入就是一本新书**——
  标注、书签、进度、阅读时长全部归零。修错别字、换更好的版本、从 epub 换成精校版，都会踩到。
  这是 Local First 阅读器里最伤的一类数据丢失：不是误删，是「做对了事却付出代价」。
- **思路**：导入结果增加第四种状态 `replaced`。
  - 检出：同一 `(sort_title, 首位作者)` 且章节文本相似度高于阈值（标题集合的 Jaccard 就够，不必全文比对）；
  - 迁移：在一个事务里把旧 `book_id` 的 `annotations` / `bookmarks` / `progress` / `reading_sessions`
    按「章序号 + 章内文本锚点」重新定位到新 `book_id`。**锚点这一步已经有现成的**——
    `textAnchor.ts::findInSections` 与 `annotation_anchor` 就是给 Kindle 标注回填铸 CFI/偏移用的同一套；
  - 决策交回读者：导入摘要里给「替换并迁移 / 两本都留 / 取消」三个出口，默认**两本都留**（不猜）。
- **优先级**：`P1`。**改动范围**：Rust `import.rs` + 一个 `library/migrate.rs`（新增）+ 一条命令参数；
  前端 `ImportSummary.tsx` 加一种状态。**0 新依赖**。
- **不做**：跨书模糊匹配、按区间折叠重复标注（与同步那边的取舍一致，罕见且可手删）。

### F3　阅读计划与剩余时间估算　`P2`

- **问题**：`pace.ts` 已经在采样阅读速度（字/分钟），`chapters.chars` 已经有全书字数，
  但这两个数字**从来没有相遇**。读者现在能看到的只有「已读 43%」，看不到「还要多久」。
- **思路**：纯派生，几乎零后端改动——
  `剩余字数 = Σ chapters.chars − 已读字数`，`剩余时间 = 剩余字数 / 当前速度`，
  再加一句「想在 N 天内读完，需要每天 X 分钟」（N 给 3 / 7 / 30 三档或一档可调）。
  落在进度条旁的副标题与统计页一个卡片上，**复用已有的阅读速度**，不再新增采样。
- **优先级**：`P2`（成本极低，感知直接）。**改动范围**：1 个 hook + 2 处文案 + 1 组单测。**0 新依赖**。
- **坑**：速度样本太少时不要显示（前 2 分钟的速度没有任何意义）—— 这是「什么时候不说」比「怎么说」更重要的一类功能。

### F4　快捷键自定义　`P2`

- **问题**：命令注册表已经是**单一事实来源**（`id / title / shortcut / run`），键盘、命令面板、菜单、右键菜单
  全从它取。差的只有一件事：读者的手不是注册表作者的手。
- **思路**：注册表不用改，只在它前面加一层覆盖表——
  - `stores/settings.ts` 里加 `keymap: Record<commandId, Shortcut[]>`（跟着 `persist` 走，与 `shelfViews` 同档）；
  - `useHotkeys` 查表时用「覆盖优先，回落到默认」；
  - 设置页一个面板：**直接复用命令面板的搜索与列表**（命令已经有 title / group / keywords），
    每行一个「录制按键」的输入框；冲突时那一行标红并说明被谁占用。
- **优先级**：`P2`（ARCHITECTURE 已把它列在 P2，这里给一条明确的低成本路径）。
  **改动范围**：settings store + `useHotkeys.ts` + 设置页一个面板。**0 新依赖**。
- **不做**：按键序列（⌘K ⌘S 这种）、上下文相关的键位、导入导出键位文件。

### F5　笔记导出到 Obsidian / Anki　`P2`

- **问题**：`library/export.rs` 已经有 md / csv 两条模板，每条标注带 `colorreader://` 深链。
  但读者的笔记最终要进的是**他自己的知识库**，而手动搬运等于没有导出。
- **思路**：不改导出管线，只加两个目标格式（由扩展名决定，与既有契约一致）：
  - `.md`（Obsidian 变体）：`[[wikilink]]` 指向书名页、标注带 `#tag`、笔记放在 `> ` 引用下面；
  - `.apkg`（Anki）：Anki 的包就是 **SQLite + 一份纯文本 `collection.anki2` 的约定**，
    rusqlite 已经在栈里，写两张表（notes / cards）+ 一个 zip 就够了；卡片正面原文、背面笔记 + 深链。
- **优先级**：`P2`。**改动范围**：`export.rs` 加两个 writer + 前端对话框加两个选项。**0 新依赖**。
- **判断**：`.apkg` 是这五个里唯一需要读一份外部格式规范的，先做 Obsidian（纯文本，半小时），
  Anki 等真有人要再做——ponytail 原则：**先做那个能被一眼审完的**。

### 3.1 代码结构

#### O1　首屏 CSS 605 KB，其中 539 KB 是 582 条字体声明　`P0`

  > 上一轮只记了「29 MB woff2」，那只是磁盘与分发成本；**真正每次启动都付的是这 539 KB 的解析与 198 KB 的传输**。
- **改法**（按代价排序，建议先做第 ① 步）：
  1. **web 构建剔除它**：`deploy-pages.yml` 已经有 `PAGES_BASE` 这个开关，在 `vite.config.ts` 里

  2. **桌面端改成可选资源**：与「读者导入字体」走同一条链（已经有 `font_import` + `/font/{id}` 协议 +
     `font-display` 重写），霞鹜文楷变成一个「一键导入」而不是「打包进去」；
  3. 至少：把这份 CSS 拆成**独立 chunk 并异步加载**（`link rel=preload` + `onload` 切换），
     不再阻塞首屏渲染。
- **优先级**：`P0`（这是唯一一条每次冷启动都在付的钱）。**改动范围**：`vite.config.ts` 1 处 + `main.tsx` 1 处

  `font-display.spec.ts` 那条 e2e 要跟着看（它覆盖的正是不该回退到别的字体）。

### 3.2 性能

#### O5　PDF 正文 backfill 没有并发上限　`P1`

- **问题**：`chapters::backfill` 在导入后由后台任务跑，实测 756 页 / 21 MB 约 **974 ms**，走的是
  `spawn_blocking` 线程池。一次性拖入 10 本 PDF，就是 10 个近 1 秒的阻塞任务同时排队；
  而它**拿的是同一把 DB 锁**（单连接 `Arc<Mutex<Connection>>`），会把书架查询也一起堵住。
- **改法**：给 backfill 加一个**串行队列 + 一次一本**（`tokio::sync::Semaphore(1)` 或一个简单的
  `Mutex<()>` 令牌），并让它在书籍被删除时可取消（队列里查一下 id 还在不在）。
  导入路径上的其它重活（哈希、字典导入）已经各自在 `spawn_blocking` 上，不用动。
- **优先级**：`P1`。**改动范围**：`chapters.rs`/`commands/book.rs` 一个调度点。**验证**：拖 5 本 PDF 计时；
  `cargo test --release bench -- --ignored --nocapture` 加一档。

#### O6　RAG 暴力点积需要一个越线门槛，而不是现在就换 ANN　`P2`

- **问题**：现在是 O(N × 768) 全扫 + 逐块 BLOB 反序列化。几千块是毫秒级，**这个设计是对的**，
  文档也写清了「等数字证明需要 ANN 时再引入」。缺的是「什么时候算证明了」。
- **改法**：`library/bench.rs` 已经有基准设施——加一档「Top-6 检索 P95」，把块数从 5k 拉到 50k
  （约 50 本大书）。**越线（比如 P95 > 100 ms）之前不动**，越线了再引 sqlite-vec（`chunks` 表形态不变）。
- **优先级**：`P2`。**改动范围**：`bench.rs` 加一档。**验证**：`cargo test --release bench -- --ignored --nocapture`。

#### O7　`cn2t` chunk 1.08 MB —— 先量，不要现在就动　`P2`

- **问题**：简繁转换的 `cn2t` chunk **1.08 MB**（`t2cn` 只有 94 KB，不对称）。已按方向懒加载，
  所以运行时不付钱；但**第一次切到繁体**要整包解析 + 常驻内存。
- **改法**：按仓库纪律「没有 Benchmark 支撑的性能结论禁止」——先量两件事：
  首次切换的耗时、常驻内存增量。**超过 300 ms 或 30 MB 才值得拆**（opencc-js 支持按档加载词典分组）。
- **优先级**：`P2`（先量后动）。**改动范围**：一条测量脚本；或 `zhConvert.ts` 的加载策略。

### 3.4 错误处理

> 上一轮清单明确写了「没有评估错误处理」，这一节是补它的。

#### O11　源资源缺失没有独立错误分支　`P0`

- **问题（实测）**：全仓 `src-tauri/src` 里对书籍源文件**没有任何存在性校验**
  （`exists()` 只出现在 `dictionaries.rs` 与 `backup.rs`）。书副本在 `<data dir>/books/` 下，
  被外部清理、备份恢复中途失败、或数据目录被挪动之后，`book_asset` / `reader_chapter` /
  `read_metadata` 抛出的是底层 IO 错误——前端拿到的是「人话 + 折叠的诊断信息」，
  但**没有「这本书的文件不见了」这个具体语义**，于是读者看到的仍是一个猜不透的失败。
- **改法**：
  1. `AppError` 加一个 `SourceMissing` 变体（它是这一档里唯一值得新增的变体：
     「文件没了」和「文件坏了」对读者的下一步完全不同）；
  2. 在 `document/mod.rs` 的 `read_asset` / `read_chapters` / `read_metadata` 里按
     `io::ErrorKind::NotFound` 映射过去（三个入口，一处收口）；
  3. 前端给三个出口：**从备份恢复 / 重新导入 / 移除条目**，而不是一句「出错了」。
- **优先级**：`P0`（改动小，但没有它时读者遇到的是一个无解的错误）。
  **改动范围**：`error.rs` 1 个变体 + 3 处映射 + 前端 1 处空状态 + 1 组单测。

#### O12　panic 兜底只在 `pdf.rs` 一处，其余六个格式的解析器同样吃不可信输入　`P1`

- **问题**：release 是 `panic = "unwind"`（`pdf.rs` 里有一条 `compile_error!` 钉着），
  而 `book_import` 处理的是**完全不可信的字节**——用户拖进来的 mobi（HUFF-CDIC 解压）、
  fb2、cbz、StarDict/MDict 词典文件，任何一个越界索引都是一次 panic，
  在 release 下就是**整个应用闪退**（2026-10-11 那次事故的形状）。目前只有 `document/pdf.rs`
  套了 `catch_unwind`。
- **改法**：**把兜底上提到调用点，而不是在七个解析器里各套一次**（ponytail：一处守卫 < 七处守卫）。
  在 `import_files` 的**单文件处理外面**套一次 `catch_unwind`，panic 转成该文件的
  `failed { reason }`，批量继续。这样：`document/` 里不需要再加任何东西，
  解析器的内部 `unwrap`（在「输入已校验」前提下的那些）也不必逐个清理。
- **优先级**：`P1`。**改动范围**：`library/import.rs` 一个包装函数 + 1 组测试
  （喂一个截断的 mobi，断言返回 `failed` 而不是进程死）。

#### O13　读取失败没有统一通路（写入失败已有）　`P2`

- **问题**：写入失败统一走 `providers.tsx` 的 `MutationCache.onError` 报 toast，这一条做得很好。
  但**读取失败**（Query error）是各页面自己写空状态——P1-9 已经为书架做过一次
  「人话 + 重试 + 折叠的诊断信息」，那套东西没有被复用。
- **改法**：把 P1-9 那一套提出来成一个 `<QueryError>` 组件，书架 / 笔记 / 搜索 / 统计四处换过去。
  **不要**做全局 Query error 拦截（那会把「这本书没有标注」也变成 toast）。
- **优先级**：`P2`。**改动范围**：1 个新组件 + 4 处替换。

### 3.5 安全性

#### O14　书源规则的 URL 没有 scheme 校验　`P1`

- **问题（实测）**：`ai/mod.rs::normalize_base_url` 有一条明确规则——**明文 `http://` 只接受 loopback，
  外网必须 TLS，否则 Key 明文过网**。而 `library/source.rs` 里 `grep` 不到任何 scheme / host 校验：
  `SourceDef::validate()`（`:74`）只校验必填规则，`full_url`（`:248`）直接拼字符串发请求。
  一份第三方书源规则因此可以把请求发往任意主机（含 `http://192.168.x.x` 这种明文内网地址），
  读者的查询词与 UA 会被送出去，`opener` 插件那个 URL 白名单**管不到 Rust 侧的 reqwest**。
- **改法**：复用 AI 那条已有的规则——把 `normalize_base_url` 提到一个共用位置
  （比如 `ai/mod.rs` 或一个 `net.rs`），`source.rs::validate` 对 `base_url` 走同一条校验。
  一条规则两处用，正是这个仓库一贯的做法。
- **优先级**：`P1`（书源是用户自己导入的第三方规则，属于信任边界）。
  **改动范围**：1 个函数搬家 + `source.rs::validate` 1 处调用 + 1 组单测。

#### O15　全库备份 zip 不加密，且明文带上所有 Key　`P1`

- **问题（实测）**：`library/backup.rs` 里没有 `argon` / `aes` / `password` 的任何痕迹——
  备份是数据目录的**原样 zip**（含书文件、词典、字体与阅读记录）。而 `settings` KV 表里存着
  **AI Key / DeepL Key / WebDAV 凭据**（明文落 SQLite）。于是「把备份放到网盘」= 明文上传整个书库 + 全部 API 凭据。
  对比：`.ctzx` 书档已经是 Argon2id + AES-256-GCM，**同一套原语没有用在备份上**。
- **改法**（两步，第二步更小但收益已经很大）：
  1. **导出时剔除 `settings` 里的凭据字段**（一条白名单/黑名单过滤 + 一条测试）。
     恢复后读者重填一次 Key，比泄露一次 Key 便宜得多；
  2. 再进一步：备份导出复用 `.ctzx` 的 Argon2id + AES-GCM，密码**可选**——不填就是现在的明文行为，
     Local First 不受影响。
- **优先级**：`P1`（先做第 1 步，`P2` 再做第 2 步）。**改动范围**：`backup.rs` 1 个过滤函数 + 1 组测试。

#### O16　capability 已经是最小权限，只剩一处需要人看一眼　`P2`

- **现状（实测）**：`capabilities/default.json` 22 条，`mini.json` 只有 4 条且只给事件与拖拽，
  `opener:allow-open-url` 带 URL 白名单，CSP 已收紧到 `default-src 'self'` + 逐源放行。
  **这一块做得比大多数 Tauri 应用好**。
- **唯一值得加的一条**：主窗口与 mini 窗口都有 `core:event:allow-emit`，悬浮条靠事件把按钮转发给主窗口。
  业务上需要，但主窗口对 `mini://*` 事件**没有 payload 形状校验**。事件订阅已经统一走
  `hooks/useTauriEvent.ts`，正好是收口的地方——在那里加一层 payload 形状检查即可。
- **优先级**：`P2`（进程内通道，风险低，属于顺手加固）。**改动范围**：`useTauriEvent.ts` 1 处。
